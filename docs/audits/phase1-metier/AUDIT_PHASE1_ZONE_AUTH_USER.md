## AuthController.authenticateUser (login)

Code audité : `controllers/AuthController.java:37-52`. Collaborateurs lus intégralement : `AuthenticationManager` (obtenu de `AuthenticationConfiguration`, `WebSecurityConfig.java:29-32`), `DaoAuthenticationProvider` (`WebSecurityConfig.java:45-51`), `UserDetailsServiceImpl` (`security/services/UserDetailsServiceImpl.java`), `UserDetailsImpl` (`security/services/UserDetailsImpl.java`), `JwtUtils` (`security/jwt/JwtUtils.java`), `UserService.isAdmin` (`services/UserService.java:48-50`), `GlobalExceptionHandler` (`exception/GlobalExceptionHandler.java`).

- **Q1 — Qui a le droit d'appeler ça, et est-ce vérifié côté serveur ?** Tout le monde, sans token. Preuve : `.requestMatchers("/api/auth/**").permitAll()` (`WebSecurityConfig.java:62`), première règle évaluée, donc gagnante pour ce chemin. C'est le comportement attendu pour un endpoint de login. Aucune limitation de débit / verrouillage de compte n'existe dans le repo (aucun `@Bean` de type rate-limiter, aucun compteur de tentatives : `UserDetailsImpl.isAccountNonLocked()` retourne `true` en dur, `security/services/UserDetailsImpl.java:46-49`) — le brute-force n'est freiné que par le coût BCrypt.
- **Q2 — Identifiant inexistant ?** `UserDetailsServiceImpl.loadUserByUsername()` lève `UsernameNotFoundException("User Not Found with email: " + username)` (`security/services/UserDetailsServiceImpl.java:22-23`). Cette exception est **interceptée par `DaoAuthenticationProvider` avant de sortir**, car `AbstractUserDetailsAuthenticationProvider.hideUserNotFoundExceptions` vaut `true` par défaut et n'est jamais désactivé dans `WebSecurityConfig.authenticationProvider()` (`WebSecurityConfig.java:45-51` — seuls `setUserDetailsService` et `setPasswordEncoder` sont appelés). Le client reçoit donc une `BadCredentialsException`, exactement comme pour un mot de passe erroné. Résultat HTTP : 401 (voir Q7).
- **Q3 — Entrée malformée ?** `@Valid @RequestBody LoginRequest` (`AuthController.java:38`) + `@NotBlank` sur `email` et `password` (`payload/request/LoginRequest.java:9-13`). Un champ vide/absent lève `MethodArgumentNotValidException`, non gérée par `GlobalExceptionHandler` donc traitée par le `DefaultHandlerExceptionResolver` de Spring MVC → **400**. Confirmé par test (voir plus bas). À noter : `LoginRequest.email` n'a **pas** d'annotation `@Email` (contrairement à `SignupRequest`), donc une chaîne arbitraire non-email passe la validation et échoue plus loin en 401 — comportement conforme (l'email est ici un identifiant opaque).
- **Q4 — Action déjà faite ?** N/A — le login est idempotent et sans effet de bord persistant. Aucune écriture BDD dans le chemin (`AuthController.java:39-51` ne contient que des lectures). Deux logins successifs produisent deux JWT valides simultanément : il n'y a **aucun stockage ni révocation de token côté serveur** (`SessionCreationPolicy.STATELESS`, `WebSecurityConfig.java:58`).
- **Q5 — Action inverse jamais faite ?** N/A — il n'existe pas d'endpoint de logout côté back (aucun `@PostMapping("/logout")` dans le repo) ; le logout est purement client (cohérent avec AUDIT_PHASE1_INVENTAIRE.md ligne 43).
- **Q6 — Propriété de la ressource ?** N/A — l'appelant s'authentifie, il ne modifie aucune ressource tierce. Le `JwtResponse` est construit exclusivement à partir du principal issu de l'authentification réussie (`AuthController.java:44-51`), jamais d'un paramètre contrôlé par le client.
- **Q7 — Erreur interprétable ou 500 ?** Trois codes possibles, tous interprétables :
  - 400 sur validation Bean Validation (Q3) ;
  - 401 sur échec d'authentification. Chaîne exacte : `BadCredentialsException` (une `AuthenticationException`) est levée par `authenticationManager.authenticate()` (`AuthController.java:39-40`) ; aucun `@ExceptionHandler` de `GlobalExceptionHandler` ne la capture (les 5 handlers déclarés couvrent `NumberFormatException`, `BadRequestException`, `NotFoundException`, `UnauthorizedException`, `ForbiddenException` — `GlobalExceptionHandler.java:12-38`) ; elle remonte donc hors du `DispatcherServlet` jusqu'à l'`ExceptionTranslationFilter`, qui délègue à l'`authenticationEntryPoint` configuré : `response.sendError(HttpServletResponse.SC_UNAUTHORIZED, exception.getMessage())` (`WebSecurityConfig.java:71-74`) → **401**. Confirmé empiriquement par deux tests d'intégration (voir plus bas).
  - 200 en cas de succès.
  Aucun chemin menant à un 500 n'a été identifié : le cast `(UserDetailsImpl) authentication.getPrincipal()` (`AuthController.java:44`) n'est atteint qu'après une authentification réussie par le `DaoAuthenticationProvider`, lequel produit toujours le `UserDetailsImpl` construit en `UserDetailsServiceImpl.java:25-33` ; `userService.isAdmin()` utilise `.map(User::isAdmin).orElse(false)` et ne peut pas lever de NPE (`services/UserService.java:49`).

**Point fuite d'information — TRANCHÉ : pas de fuite.** Le message d'erreur ne permet **pas** de distinguer « email inconnu » de « mot de passe incorrect ». Trois preuves cumulatives :
1. `hideUserNotFoundExceptions = true` (défaut Spring Security 6.x, jamais surchargé dans `WebSecurityConfig.java:45-51`) convertit `UsernameNotFoundException` en `BadCredentialsException` — le message spécifique `"User Not Found with email: …"` construit en `UserDetailsServiceImpl.java:23` n'atteint donc jamais le client.
2. Les deux cas produisent le **même code HTTP 401** — prouvé par les deux tests `AuthControllerIT.login_returns401_whenPasswordIsWrong` (`controllers/AuthControllerIT.java:171-184`) et `AuthControllerIT.login_returns401_whenEmailIsUnknown` (`controllers/AuthControllerIT.java:186-195`).
3. Le corps de réponse ne contient pas non plus le message : `sendError(401, message)` (`WebSecurityConfig.java:73`) délègue à la page d'erreur du conteneur ; `application.yml` (`back/src/main/resources/application.yml`) ne définit aucune propriété `server.error.include-message`, qui vaut donc `never` par défaut en Spring Boot 3 — le champ `message` est omis du JSON d'erreur. Et même s'il était inclus, il vaudrait `"Bad credentials"` dans les deux cas (point 1).

Réserve honnête sur la portée : cette conclusion porte sur le **canal message/code HTTP**. Le canal temporel n'a pas été mesuré ; il est cependant couvert par `DaoAuthenticationProvider.mitigateAgainstTimingAttack()`, qui exécute un encodage BCrypt factice quand l'utilisateur est introuvable — comportement du framework, non modifié ici. Aucun test du repo ne mesure les temps de réponse.

**Point sécurité mot de passe — TRANCHÉ : comparaison sûre, aucune comparaison en clair.** La vérification est intégralement déléguée au `DaoAuthenticationProvider`, dont l'encodeur est le `BCryptPasswordEncoder` du contexte (`WebSecurityConfig.java:41-43` et `:49`). Le contrôleur ne compare **jamais** de mot de passe lui-même : `AuthController.java:39-52` ne contient aucun `equals`, aucune comparaison de chaîne — le seul usage de `loginRequest.getPassword()` est son passage au `UsernamePasswordAuthenticationToken` (`AuthController.java:40`). Le hash stocké est celui chargé en base (`UserDetailsServiceImpl.java:32`). Le mot de passe en clair n'est ni journalisé ni renvoyé : `UserDetailsImpl.password` porte `@JsonIgnore` (`security/services/UserDetailsImpl.java:31-32`) et `JwtResponse` ne l'inclut pas (`AuthController.java:46-51` — seuls jwt, id, username, firstName, lastName, admin).

**Point corps de réponse en cas d'échec — TRANCHÉ : générique, aucune stack trace.** Voir Q7 et point 3 ci-dessus. Aucune exception applicative n'est sérialisée : `GlobalExceptionHandler` ne renvoie de corps que pour `BadRequestException` avec message non-blanc (`GlobalExceptionHandler.java:19-21`), cas qui ne se produit pas sur le login. Les autres handlers renvoient des réponses **sans corps** (`.build()`). Aucun `printStackTrace`, aucun `e.toString()` renvoyé au client dans cette zone.

**Scénario reproductible si problème** : aucun problème de fuite d'information ni de comparaison de mot de passe identifié → aucun scénario à décrire. Le seul point notable (absence de rate-limiting / verrouillage de compte, Q1) ne se prête pas au test de départage de METHODE_AUDIT.md : je peux l'argumenter mais **pas écrire un test rouge exprimant un comportement attendu**, puisque aucun comportement de limitation n'est spécifié nulle part dans le projet (ni énoncé, ni testing plan). Argument sans scénario.

**Tests existants couvrant ces points** :
- `AuthControllerIT.login_returns200AndJwtResponse_whenCredentialsAreValid` (`controllers/AuthControllerIT.java:142-169`) — prouve : 200, contenu exact du `JwtResponse` (id/username/firstName/lastName/admin/type), et que le token renvoyé est **cryptographiquement valide** (`jwtUtils.validateJwtToken(token)` ligne 166) avec le bon subject (ligne 168). Ne prouve rien sur le hachage côté login.
- `AuthControllerIT.login_returns401_whenPasswordIsWrong` (`:171-184`) — prouve : mot de passe erroné → 401, sur un utilisateur **réellement persisté avec un mot de passe encodé BCrypt** (`persistUser()` ligne 76-84 utilise `passwordEncoder.encode(rawPassword)`). C'est la preuve indirecte que la comparaison BCrypt fonctionne : le hash stocké ne correspond pas au clair envoyé.
- `AuthControllerIT.login_returns401_whenEmailIsUnknown` (`:186-195`) — prouve : email inexistant → 401, **identique** au cas précédent. C'est le test qui verrouille l'absence de fuite d'information au niveau du code HTTP.
- `AuthControllerIT.login_returns400_whenPasswordIsBlank` (`:197-206`) — prouve : la validation `@NotBlank` produit bien un 400 et non un 401, ce qui garantit que les deux tests 401 ci-dessus isolent bien l'échec d'authentification (raisonnement explicité dans les commentaires du fichier, lignes 176-179 et 188-190).
- **Non couvert** : le contenu exact du corps de réponse en 401 (aucun `jsonPath`/`content()` asserté sur les tests 401) — la conclusion « corps générique » repose ici sur la lecture de code + le défaut `server.error.include-message=never`, pas sur une assertion de test. Nuance à connaître.

## AuthController.registerUser (register)

Code audité : `controllers/AuthController.java:54-59`, `payload/request/SignupRequest.java`, `services/UserService.java:56-62`, `models/User.java`.

- **Q1 — Qui a le droit d'appeler ça ?** Tout le monde, sans token (`permitAll`, `WebSecurityConfig.java:62`) — conforme à un endpoint d'inscription publique. Point de sécurité positif à noter : **le client ne peut pas s'auto-promouvoir admin**. `SignupRequest` ne comporte aucun champ `admin` (`payload/request/SignupRequest.java:11-28` : email, firstName, lastName, password uniquement) et `UserService.register()` passe `false` en dur au constructeur (`services/UserService.java:60`). Un JSON contenant `"admin":true` serait simplement ignoré à la désérialisation.
- **Q2 — Identifiant inexistant ?** N/A — création, aucun identifiant en entrée.
- **Q3 — Entrée malformée ? TRANCHÉ : validation présente, déclarative, exécutée avant toute écriture BDD.** `@Valid @RequestBody SignupRequest` (`AuthController.java:55`) déclenche la Bean Validation **avant** l'entrée dans le corps de méthode ; le contrôleur n'est jamais atteint si elle échoue, donc `userService.register()` (donc le `save()`) n'est pas appelé. Annotations exactes sur `payload/request/SignupRequest.java` :
  | Champ | Contraintes | Lignes |
  |---|---|---|
  | `email` | `@NotBlank`, `@Size(max = 50)`, `@Email` | 12-15 |
  | `firstName` | `@NotBlank`, `@Size(min = 3, max = 20)` | 17-19 |
  | `lastName` | `@NotBlank`, `@Size(min = 3, max = 20)` | 21-23 |
  | `password` | `@NotBlank`, `@Size(min = 6, max = 40)` | 25-27 |
  Il s'agit donc bien d'annotations Bean Validation sur le DTO de payload, **pas** d'une vérification manuelle dans le service (`UserService.register()` ne contient aucune validation de format, `services/UserService.java:56-62`). Sur le format de l'email : `@Email` est présent (contrainte de format). Sur le mot de passe : **longueur minimale 6 uniquement, aucune contrainte de complexité** (pas de `@Pattern`, aucune règle majuscule/chiffre/caractère spécial nulle part dans le repo). Cohérence entité/DTO vérifiée : `User.password` accepte `@Size(max = 120)` (`models/User.java:64`), largement supérieur à un hash BCrypt de 60 caractères — pas de risque de troncature.
- **Q4 — Action déjà faite (email déjà pris) ? TRANCHÉ : vérification explicite en amont, pas de remontée d'exception SQL brute.** `UserService.register()` commence par `if (existsByEmail(email)) throw new BadRequestException("Error: Email is already taken!")` (`services/UserService.java:57-59`), avant l'encodage et avant le `save()` (`:60-61`). Cette `BadRequestException` est captée par `GlobalExceptionHandler.handleBadRequestException` qui, le message étant non-blanc, renvoie **400 avec un corps `MessageResponse`** (`exception/GlobalExceptionHandler.java:17-23`). Le client reçoit `{"message":"Error: Email is already taken!"}` — jamais une `SQLIntegrityConstraintViolationException`. La contrainte unique BDD existe bien en défense en profondeur (`@UniqueConstraint(columnNames = "email")`, `models/User.java:30-32`), mais n'est pas le mécanisme de premier niveau.
  **Réserve à signaler (fenêtre TOCTOU)** : entre le `existsByEmail()` (`:57`) et le `save()` (`:61`) il n'y a **aucune transaction ni verrou** — `UserService` ne porte pas `@Transactional` (`services/UserService.java:14-22`, seule annotation : `@Service`). Deux requêtes `register` concurrentes avec le même email peuvent donc franchir toutes deux le `existsByEmail`, et la seconde échouer sur la contrainte unique avec une `DataIntegrityViolationException` — non gérée par `GlobalExceptionHandler` (aucun handler ne la couvre, `:12-38`) → **500 avec un corps d'erreur Spring Boot générique**. Voir « Scénario reproductible » ci-dessous pour le statut de départage.
- **Q5 — Action inverse jamais faite ?** N/A — pas d'action inverse au register côté auth (la suppression de compte relève de `DELETE /api/user/{id}`, traitée plus bas).
- **Q6 — Propriété de la ressource ?** N/A — l'appelant crée sa propre ressource, il n'y a pas de ressource préexistante dont il pourrait ne pas être propriétaire.
- **Q7 — Erreur interprétable ou 500 ?** 200 (succès, corps `MessageResponse` explicite, `AuthController.java:58`), 400 avec message métier (email déjà pris, Q4), 400 sans corps détaillé (violation Bean Validation → `MethodArgumentNotValidException` → `DefaultHandlerExceptionResolver`, Q3). Le seul 500 identifié est la fenêtre TOCTOU concurrente ci-dessus. Nuance sur l'interprétabilité côté front : les 400 de validation et le 400 « email déjà pris » se distinguent par la **présence ou l'absence du corps `message`**, pas par le code HTTP — le front ne peut donc pas dire « email invalide » vs « email déjà pris » sur le seul code de statut.

**Point fuite d'information** : le message `"Error: Email is already taken!"` constitue par nature une **énumération de comptes sur l'endpoint d'inscription** (un tiers non authentifié peut tester si un email est enregistré). C'est le comportement standard d'un formulaire d'inscription (le retour est nécessaire à l'UX) et il est explicitement verrouillé par un test existant — signalé pour complétude, pas comme anomalie.

**Point sécurité mot de passe — TRANCHÉ : haché avant écriture en BDD, aucun stockage en clair.** Preuve directe : `new User(email, lastName, firstName, passwordEncoder.encode(rawPassword), false)` (`services/UserService.java:60`) — l'appel `passwordEncoder.encode()` est **dans l'expression de construction**, le mot de passe brut n'est jamais assigné à l'entité. Le `PasswordEncoder` injecté est le `BCryptPasswordEncoder` unique du contexte (`services/UserService.java:19-22` ← `WebSecurityConfig.java:41-43`). Le `save()` intervient à la ligne suivante (`:61`), après encodage. Preuve empirique par test d'intégration sur base réelle : `AuthControllerIT.register_returns200AndSuccessMessage_whenDataIsValid` relit l'utilisateur en base et asserte `saved.getPassword()).isNotEqualTo("password123")` **et** `passwordEncoder.matches("password123", saved.getPassword())).isTrue()` (`controllers/AuthControllerIT.java:98-100`) — c'est la preuve la plus forte disponible : le clair n'est pas stocké, et ce qui est stocké est bien un hash vérifiable.

**Scénario reproductible si problème** : un seul point ouvert, la fenêtre TOCTOU du Q4.
- Description du scénario : (1) choisir un email non encore enregistré ; (2) envoyer **simultanément** deux `POST /api/auth/register` avec ce même email depuis deux clients ; (3) l'un des deux répond 500 au lieu de 400 « Email is already taken! ».
- **Statut de départage — honnête : scénario décrit en 3 étapes mais NON déterministe.** Le test de départage de METHODE_AUDIT.md demande « peux-tu écrire un test qui échoue aujourd'hui et devrait passer ? ». Ici le test serait *flaky par construction* : il dépend d'un entrelacement réel des deux transactions, non garanti. Je ne peux donc pas produire un test rouge fiable — c'est un argument étayé par lecture de code (absence de `@Transactional`, absence de handler pour `DataIntegrityViolationException`), **pas** un scénario reproductible au sens strict de la grille. À arbitrer en tenant compte du fait qu'un projet OpenClassrooms mono-utilisateur n'exerce jamais cette fenêtre.

**Tests existants couvrant ces points** :
- `AuthControllerIT.register_returns200AndSuccessMessage_whenDataIsValid` (`controllers/AuthControllerIT.java:88-102`) — prouve : 200, message exact, **hachage BCrypt effectif en base** (lignes 99-100), et `admin = false` par défaut (ligne 101, ce qui verrouille l'impossibilité d'auto-promotion vue en Q1).
- `AuthControllerIT.register_returns400AndMessage_whenEmailIsAlreadyTaken` (`:104-114`) — prouve : le doublon d'email produit un **400 avec le message métier**, donc que la branche `existsByEmail` est bien prise et qu'aucune exception SQL brute ne remonte. C'est le test qui tranche le Q4.
- `AuthControllerIT.register_returns400_whenEmailIsBlank` (`:116-122`) — prouve : `@NotBlank` sur email actif.
- `AuthControllerIT.register_returns400_whenEmailFormatIsInvalid` (`:124-130`) — prouve : `@Email` actif (chaîne `"not-an-email"` rejetée). C'est le test qui tranche la partie « format d'email » du Q3.
- `AuthControllerIT.register_returns400_whenPasswordIsTooShort` (`:132-138`) — prouve : `@Size(min = 6)` sur password actif (`"abc"` rejeté). Tranche la partie « longueur de mot de passe » du Q3.
- `UserServiceTest.should_saveUserWithEncodedPassword_when_registerIsCalled_and_emailIsNotTaken` (`services/UserServiceTest.java:177-193`) — unitaire, mocks purs ; prouve via `ArgumentCaptor` que l'entité passée au `save()` porte le mot de passe **encodé** et `admin=false`, et que `passwordEncoder.encode()` est appelé exactement une fois.
- `UserServiceTest.should_throwBadRequestException_when_registerIsCalled_and_emailIsAlreadyTaken` (`:195-204`) — prouve que sur doublon, **ni `encode()` ni `save()` ne sont appelés** (`verify(..., never())`) : la vérification est bien en amont de toute écriture.
- **Non couvert** : `@Size(min = 3)` sur firstName/lastName ; `@Size(max = 50)` sur email ; la fenêtre TOCTOU concurrente (par nature non testable de façon déterministe).

## UserController — GET /api/user/{id} (findById)

Code audité : `controllers/UserController.java:28-32`, `services/UserService.java:36-38`, `mapper/UserMapper.java`, `dto/UserDto.java`, `exception/GlobalExceptionHandler.java`.

- **Q1 — Qui a le droit d'appeler ça, et est-ce vérifié côté serveur ? Point à signaler.** Authentification seule, aucune restriction supplémentaire. Preuve d'absence, par lecture exhaustive : la méthode `findById` (`controllers/UserController.java:28-32`) ne lit **aucun** principal (pas de `SecurityContextHolder`, contrairement à `save`/delete ligne 36 du même fichier), ne porte aucune annotation `@PreAuthorize` (aucune occurrence de `@PreAuthorize` dans tout le repo — cf. note transverse AUDIT_PHASE1_INVENTAIRE.md ligne 23), et `UserService.findById()` se réduit à `userRepository.findById(id).orElseThrow(NotFoundException::new)` (`services/UserService.java:36-38`) sans le moindre contrôle d'appelant. **Conséquence factuelle : n'importe quel utilisateur authentifié peut lire la fiche de n'importe quel autre utilisateur** en itérant sur les identifiants — email, nom, prénom, statut admin, dates de création/mise à jour.
  Comparaison demandée avec le fix P1-01 : `SessionService.assertRequestingUserIsSelf()` (`services/SessionService.java:93-98`) existe et est appelé sur `participate`/`noLongerParticipate` ; `UserService.deleteById()` a son équivalent (`:30-32`) ; **`findById` n'a aucun équivalent**. C'est une asymétrie de traitement au sein même de `UserService` : la lecture n'est pas protégée alors que la suppression l'est.
- **Q2 — Identifiant inexistant ?** `orElseThrow(NotFoundException::new)` (`services/UserService.java:37`) → `GlobalExceptionHandler.handleNotFoundException` → **404 sans corps** (`exception/GlobalExceptionHandler.java:25-28`). Confirmé par test.
- **Q3 — Entrée malformée ?** `Long.valueOf(id)` sur un `@PathVariable("id") String` (`controllers/UserController.java:29-30`) lève `NumberFormatException` → `GlobalExceptionHandler.handleNumberFormatException` → **400 sans corps** (`GlobalExceptionHandler.java:12-15`). Même mécanisme que `SessionController.findById`. Confirmé par test.
- **Q4 — Action déjà faite ?** N/A — lecture seule, idempotente, aucune écriture BDD dans le chemin.
- **Q5 — Action inverse jamais faite ?** N/A.
- **Q6 — Propriétaire de la ressource ?** **Non vérifié** — voir Q1. L'endpoint est en lecture, donc aucune modification illégitime n'est possible ; le sujet est ici la confidentialité, pas l'intégrité.
- **Q7 — Erreur interprétable ou 500 ?** 200 / 404 (inexistant) / 400 (id non numérique) / 401 (non authentifié) — tous interprétables et tous couverts par test. Aucun chemin vers un 500 identifié : le mapper MapStruct opère sur une entité non-nulle garantie par l'`orElseThrow`.

**Point exposition de champs sensibles — TRANCHÉ : le mot de passe n'est PAS exposé, y compris haché.** Chaîne de preuve complète :
1. `UserMapper` est une interface MapStruct nue (`mapper/UserMapper.java:10-11`, aucun `@Mapping` d'exclusion) : l'implémentation générée **copie bien `User.password` vers `UserDto.password`** — le champ est donc présent dans l'objet DTO en mémoire.
2. Mais `UserDto.password` porte `@JsonIgnore` (`dto/UserDto.java:35-37`) : Jackson l'exclut à la sérialisation. Le champ n'apparaît donc **pas** dans le JSON renvoyé par `ResponseEntity.ok().body(this.userMapper.toDto(user))` (`controllers/UserController.java:31`).
3. Preuve empirique, sur base réelle et via la vraie pile de sérialisation : `UserControllerIT.findById_returns200AndUserDto_whenUserExists` asserte `jsonPath("$.password").doesNotExist()` (`controllers/UserControllerIT.java:61`, commentée lignes 59-60 comme point de vigilance explicite).
Fragilité à signaler malgré tout : la protection repose sur **une seule annotation Jackson** sur le DTO, pas sur une exclusion au niveau du mapping. Supprimer `@JsonIgnore` (`dto/UserDto.java:35`) exposerait immédiatement le hash BCrypt sur cet endpoint public à tout utilisateur authentifié. Le test ligne 61 est précisément la digue qui rendrait cette régression rouge — il est donc à conserver.
Les autres champs bien exposés : `id`, `email`, `lastName`, `firstName`, `admin`, `createdAt`, `updatedAt` (assertés `UserControllerIT.java:52-58`). L'`email` et le flag `admin` d'un tiers sont donc lisibles par tout utilisateur authentifié — c'est la substance du point Q1.

**Scénario reproductible si problème** (Q1/Q6, lecture de la fiche d'un tiers) :

## UserController — DELETE /api/user/{id} (méthode `save`)

Code audité : `controllers/UserController.java:34-39`, `services/UserService.java:28-34`, `exception/UnauthorizedException.java`, `exception/ForbiddenException.java`, `services/SessionService.java:93-98` (pour comparaison), `models/Session.java:67-72` (relation PARTICIPATE).

- **Q1 — Qui a le droit d'appeler ça, et est-ce vérifié côté serveur ?** Authentification (règle `/api/**` → `authenticated()`, `WebSecurityConfig.java:67`) **plus** un contrôle applicatif de propriété. Le contrôleur lit le principal — `(UserDetails) SecurityContextHolder.getContext().getAuthentication().getPrincipal()` (`controllers/UserController.java:36`) — et transmet `userDetails.getUsername()` au service (`:37`). Aucun rôle admin n'est requis ni vérifié : **un administrateur ne peut pas non plus supprimer le compte d'un tiers** (le test d'égalité `:30` ne comporte pas d'échappatoire admin). C'est une décision de conception à noter, pas nécessairement un défaut.
- **Q2 — Identifiant inexistant ?** `deleteById()` appelle d'abord `findById(id)` (`services/UserService.java:29`), qui lève `NotFoundException` → **404** (`GlobalExceptionHandler.java:25-28`). Confirmé par test. Ordre à noter : la vérification d'existence précède la vérification d'autorisation (`:29` avant `:30`), donc un appelant non propriétaire distingue « id inexistant » (404) de « id existant mais pas le mien » (401) — canal d'énumération d'identifiants. Portée réelle nulle en pratique : `GET /api/user/{id}` fournit déjà la même information de façon plus directe (voir endpoint précédent).
- **Q3 — Entrée malformée ?** `Long.parseLong(id)` (`controllers/UserController.java:37`) → `NumberFormatException` → **400** (`GlobalExceptionHandler.java:12-15`). Confirmé par test. Ordre d'évaluation : la lecture du principal (`:36`) précède le parsing (`:37`), donc un appel non authentifié avec un id invalide donne 401 (bloqué par le filtre en amont), jamais 400 — cohérent.
- **Q4 — Action déjà faite (supprimer un compte déjà supprimé) ?** Le second appel repasse par `findById` (`services/UserService.java:29`) qui ne trouve plus rien → **404**. Comportement déterministe et correct, mais **non couvert par un test dédié** (aucun test `delete_returns404_whenCalledTwice` dans `UserControllerIT.java`) ; il se déduit du chemin de code et du test `delete_returns404_whenUserDoesNotExist` (`:124-131`), qui exerce exactement le même chemin.
- **Q5 — Action inverse jamais faite ?** N/A — la suppression de compte n'a pas d'inverse (aucun endpoint de restauration, aucun soft-delete : `userRepository.deleteById(id)` est une suppression physique, `services/UserService.java:33`).
- **Q6 — Propriétaire de la ressource ? TRANCHÉ : OUI, le contrôle existe.** `if (!Objects.equals(currentUsername, user.getEmail())) throw new UnauthorizedException();` (`services/UserService.java:30-32`), placé **avant** le `deleteById()` (`:33`) — l'écriture n'a donc pas lieu en cas de rejet. **Ce n'est PAS un angle mort équivalent à P1-01.** Comparaison factuelle avec le fix `SessionService.assertRequestingUserIsSelf()` :
  | Aspect | `SessionService.assertRequestingUserIsSelf` (`services/SessionService.java:93-98`) | `UserService.deleteById` (`services/UserService.java:28-34`) |
  |---|---|---|
  | Source de l'identité | `SecurityContextHolder` lu **dans le service** (`:94`) | `SecurityContextHolder` lu **dans le contrôleur** (`controllers/UserController.java:36`), username passé en paramètre |
  | Clé de comparaison | `userDetails.getId()` vs `userId` — identifiant numérique (`:95`) | `currentUsername` vs `user.getEmail()` — chaîne email (`:30`) |
  | Type de cast | `(UserDetailsImpl)` (cast concret — cf. P1-05) | `(UserDetails)` (interface Spring — cast plus large, donc plus robuste) |
  | Exception levée | `ForbiddenException` → **403** (`exception/ForbiddenException.java`, `GlobalExceptionHandler.java:35-38`) | `UnauthorizedException` → **401** (`exception/UnauthorizedException.java`, `GlobalExceptionHandler.java:30-33`) |
  Deux écarts se dégagent, à arbitrer : (a) **incohérence sémantique de code HTTP** — le même refus métier « ce n'est pas ta ressource » renvoie 403 côté session et 401 côté user, alors que 401 signifie « non authentifié » (or l'appelant l'est) ; (b) **comparaison par email plutôt que par id** — fonctionnellement correcte aujourd'hui puisque l'email porte une contrainte unique (`models/User.java:30-32`) et que le subject du JWT est l'email (`security/jwt/JwtUtils.java:31`), mais plus fragile qu'une comparaison d'identifiants (sensible à la casse selon la collation MySQL, et cassée par toute future fonctionnalité de changement d'email).
- **Q7 — Erreur interprétable ou 500 ? Point à signaler.** Cas nominaux interprétables : 200, 404, 401 (non propriétaire), 400 (id non numérique), 401 (non authentifié) — tous testés. **Mais un chemin vers un 500 est identifié : la suppression d'un utilisateur inscrit à au moins une session.** Chaîne de preuve par lecture :
  1. La relation `Session ↔ User` est un `@ManyToMany(fetch = EAGER)` avec `@JoinTable(name = "PARTICIPATE", …)` **porté par `Session`** (`models/Session.java:67-72`) — `Session` est le côté propriétaire.
  2. `User` (`models/User.java`) ne déclare **aucune** relation inverse vers `Session` : pas de `@ManyToMany(mappedBy = …)`, donc **aucun cascade ni orphanRemoval** ne peut nettoyer les lignes de `PARTICIPATE` lors de la suppression d'un `User`.
  3. `UserService.deleteById()` appelle directement `userRepository.deleteById(id)` (`services/UserService.java:33`) sans purger au préalable les participations (aucun `SessionRepository` n'est injecté dans `UserService`, `:16-22`).
  4. Le schéma est généré par Hibernate (`ddl-auto: update`, `back/src/main/resources/application.yml`) — aucun script DDL versionné ne définit `PARTICIPATE` (seuls `insert_teacher.sql` et `insert_user.sql` existent dans `back/src/main/resources/sql/`). Hibernate génère par défaut les contraintes de clé étrangère d'une table de jointure `@JoinTable`.
  5. Une `DataIntegrityViolationException` n'est couverte par **aucun** handler de `GlobalExceptionHandler` (les 5 handlers sont listés `:12-38`) → réponse 500.

**Point exposition de champs sensibles** : N/A pour cet endpoint — la réponse de succès est `ResponseEntity.ok().build()` (`controllers/UserController.java:38`), **corps vide**. Aucune donnée utilisateur n'est renvoyée.

**Point angle mort DELETE user — TRANCHÉ** : la question posée (« un utilisateur peut-il supprimer un autre compte que le sien ? ») a une réponse **non**, prouvée à la fois par lecture (`services/UserService.java:30-32`) et par un test d'intégration dédié utilisant deux comptes réellement distincts (`UserControllerIT.delete_returns401_whenUserTriesToDeleteAnotherUsersAccount`, lignes 108-122, avec assertion `assertThat(userA.getEmail()).isNotEqualTo(userB.getEmail())` ligne 112 qui exclut le piège du faux positif, et vérification post-appel que userB **existe toujours** ligne 121). Il n'y a donc pas de vulnérabilité d'autorisation analogue à P1-01 sur cet endpoint. Les points restants sont d'un autre ordre : cohérence du code HTTP (401 vs 403), clé de comparaison (email vs id), et intégrité référentielle (Q7).

**Scénarios reproductibles si problème** :

*Scénario 1 — 500 sur suppression d'un compte participant à une session (Q7)* :

Le maillon non vérifiable par lecture seule est l'existence effective de la contrainte FK générée par Hibernate sur `PARTICIPATE` (comportement par défaut, mais dépendant du moteur et de `ddl-auto: update` sur un schéma préexistant). **À confirmer par Postman ou par un test d'intégration dédié avant tout arbitrage** — exactement la même précaution que celle qui avait été prise pour P1-02, dont le diagnostic final (`ObjectOptimisticLockingFailureException`) n'avait pu être établi qu'à l'exécution.
